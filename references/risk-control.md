# 京东风控阈值与恢复策略

> 数据来源：2026-10-23 单账号实测（真实浏览器 + 已登录会话）。

## 一、实测时间线

| 时间 | 动作 | 结果 |
|---|---|---|
| ~12:12 | 连续抓 11–13 个商品详情页（间隔约 8s） | 触发封禁：跳 `trade.m.jd.com/common/limit.html` |
| 13:04 | 单 SKU 探测 | 仍封 |
| 13:08 | 单 SKU 探测 | 仍封 |
| 13:12:42 | 换 SKU 探测（距首次封禁约 60 分钟） | **解封**，成功取到 ¥9999 |
| 13:12:47 | 紧接着下一个 SKU | **立即再封** |
| 14:20 | 搜索 "iPhone 18" | 正常，返回 30 条 |
| 14:25–14:35 | 连续 6 次搜索（不同关键词） | 全部 **0 条** |
| 14:30 | 复查已知可用词 "iPhone" | **也 0 条** → 搜索被软封 |

## 二、阈值表（推荐值，已留余量）

| 通道 | 安全值 | 实测依据 |
|---|---|---|
| 商品详情页 | **1 个 / 次，间隔 ≥60 分钟，每天 ≤8–10 个** | 解封后只够 1 个 |
| 搜索页 | **间隔 ≥45 秒，单轮 ≤6 个关键词** | 连续 6 次后 0 条 |
| 单日总量 | 搜索 ≤60 次、详情 0 次（本仓库不用详情页） | — |
| 触发后静置 | **≥2 小时**，再从 1 个关键词单条重测 | 60 分钟不足以恢复搜索 |

> 结论：**8–10 个新 SKU/天** 是可持续上限。想多铺，就要多账号或多天。

## 三、封禁信号识别

| 现象 | 含义 | 处理 |
|---|---|---|
| URL 跳到 `trade.m.jd.com/common/limit.html`，页面文案「活动火爆 请选购其他商品」 | 详情页封禁 | 立即停手 ≥60 分钟 |
| 搜索页 URL 正常、标题正常，但 `document.querySelectorAll('[data-sku]').length === 0` | 搜索软封 | 立即停止整轮，静置 ≥2 小时 |
| `item.jd.com` 跳到 `jd.com/error2.aspx?from=shopdomain` | PC 端被拦 | 同详情页，停手 |
| 跳 `plogin.m.jd.com/login` | 登录态失效 | 让用户在 Chrome 里重新登录京东 |

## 四、本仓库的工程化对策

1. **完全不使用详情页** —— 价格只从搜索页列表取（`jd_search.py`）。
2. **熔断优先于重试** —— 任一次返回 0 条立即 `break`，不再发请求。
3. **单轮上限** —— `--max-kw` 默认 6；节流 `--throttle` 默认 45 秒。
4. **价格体检** —— 剔除 < 门槛价、带小数点的分期价、标题含「预约/定金/秒杀/需签收激活」的条目。
5. **状态落盘** —— `data/search_summary.json` 记录 `stopped` 与时间戳，便于隔天续跑。

## 五、当日恢复 SOP

```bash
# 1) 静置 2 小时后，单条试探（不要批量）
python scripts/jd_search.py --keywords "iPhone 18" --max-kw 1 --throttle 0

# 2) 看 data/search_summary.json：total 应为 30 左右
#    total=0 → 继续静置，别再试
#    total>0 → 恢复，按 45 秒/词 正常跑一轮（≤6 词）

python scripts/jd_search.py --scope scope.jsonc --max-kw 6
```

## 六、不要做的事

- ❌ 封禁期间连续重试「试试好了没」——会累积、延长封禁
- ❌ 抓详情页来"核对价格"——这是最贵的操作，一天只有 8–10 次额度
- ❌ 多开标签页并发搜京东——等同瞬间高频
- ❌ 用无头浏览器/新指纹硬刚——登录态与风险分绑在账号上，换浏览器只会要求重新登录
